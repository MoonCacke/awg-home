# Безопасность

## Никогда не публиковать

- AWG/WireGuard private key и preshared key;
- VLESS UUID действующего клиента;
- REALITY private key, public key/password и short ID в одной связке;
- готовые `vless://` URI и QR-коды;
- Telegram/API-токены, пароли и cookies;
- приватные SSH-ключи;
- полный рабочий инвентарь пользователей и адресов;
- резервные копии `/etc` без предварительной очистки.

Публичный ключ AWG сам по себе не является закрытым ключом, но его публикация
раскрывает структуру и идентификатор peer, поэтому в публичной документации
лучше использовать плейсхолдер.

## SSH

- вход только по ключам;
- `PasswordAuthentication no` после проверки второго рабочего сеанса;
- отдельный пользователь вместо повседневного root;
- минимальный sudo, где возможно;
- firewall ограничивает SSH доверенными адресами или VPN;
- fail2ban — дополнительный слой, а не замена ключам и firewall.

Не отключайте root/password удалённо, пока не проверен вход новым ключом в
отдельном терминале.

## Firewall

Открывайте только:

- административный SSH-порт;
- UDP-порт AWG;
- TCP-порт VLESS REALITY;
- HTTP/HTTPS, только если сервер действительно публикует сайт.

Входящий трафик из клиентского VPN не должен получать доступ ко всей LAN без
явной необходимости.

## Проверка перед Git

```bash
git status --short
git diff --cached
git ls-files
rg -n '(PrivateKey|PresharedKey|BEGIN .*PRIVATE KEY|vless://|token|password)' .
```

Полезно дополнительно запускать `gitleaks` или аналогичный secret scanner.
Если секрет когда-либо попал в публичный commit, простого удаления файла
недостаточно: секрет нужно немедленно заменить, а историю очищать отдельно.
